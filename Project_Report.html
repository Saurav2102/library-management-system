Abstract

Manual record keeping and un-normalized spreadsheet solutions within academic libraries introduce severe operational overhead, data redundancy, and calculation inconsistencies during circulation management.

This DBMS project implements Library Management System, a robust, full-stack database application developed for academic libraries. The system is architected on a decoupled Three-Tier Model:

  • Presentation Tier: High-efficiency Vanilla JavaScript, responsive CSS3 variables (supporting light/dark themes), real-time debounced lookups, continuous sequential numbering (#1, #2, #3...), and instant CSV export.
  • Application Tier: Node.js runtime with Express.js REST API layer enforcing parameterized SQL query binding against SQL injection vulnerabilities and robust request validation.
  • Data Tier: Production-grade PostgreSQL database leveraging ACID transactions, pg.Pool connection pooling, declarative domain CHECK constraints, unique ISBN keys, and automatic sequence generation.

The production instance is populated with 221 authentic textbooks and reference materials across eight academic disciplines. Deployed live on Render with SSL/TLS transport security, the system guarantees instant sub-100ms response times, automated loan renewal, and real-time overdue fine computations.

Chapter 1: Introduction

1.1 Project Overview

An academic library serves as the central information repository for a modern technical university. In universities like K.R. Mangalam University, maintaining an organized and automated system for thousands of books, engineering references, machine learning research papers, and literary works is crucial to student learning and faculty research.

This DBMS Project presents the design and realization of a responsive, full-stack Library Management System. Built with a production-grade PostgreSQL relational database and an Express.js backend, the system digitizes book acquisition, student circulation, loan renewals, overdue fines, and data export into a unified, secure dashboard.

1.2 Problem Statement

Traditional libraries commonly rely on physical card ledgers or desktop spreadsheets. These methods suffer from critical vulnerabilities:

  • Concurrency Hazards: Simultaneous checkout attempts by multiple librarians lead to file lockups and lost updates.
  • Absence of Domain Constraints: Spreadsheets cannot enforce unique ISBNs or restrict circulation status, allowing corrupted records.
  • Manual Penalty Arithmetic: Librarians must manually count days past due to assess fines, resulting in human error and lost revenue.
  • Data Loss: Local files lack transaction atomicity (ACID), automatic cloud backups, and connection encryption.

1.3 Objectives & Purpose

Under the mentorship of Ms. Mansi Kajal, the project achieved the following key objectives:

  1. True Relational CRUD Operations: Executing real SQL queries (INSERT, SELECT, UPDATE, DELETE) with ACID compliance against PostgreSQL.
  2. Circulation & Loan Tracking: One-click book checkout and return with student borrower IDs and customizable loan periods.
  3. Dynamic Overdue & Fine Auditing: Automatic calculation of past-due days and fine charges ($1.00/day) directly in the SQL engine.
  4. Data Portability: Native export of catalog records to standard RFC 4180 CSV files.
  5. Cloud Production Deployment: Live hosting on Render with SSL/TLS encryption and GitHub CI/CD integration.

1.4 Scope and Applicability

The project serves as an institutional library dashboard supporting full catalog lookup, real-time filtering, dual view modes (Table and Grid), dark mode, and loan extensions. Future phases will incorporate automated email notifications and barcode scanner hardware.

2.3 Technology Stack Justification

PostgreSQL: Chosen for its strict ACID compliance, robust sequence generators (SERIAL), declarative CHECK constraints, and proven reliability for institutional data.

Node.js & Express.js: The asynchronous, non-blocking I/O event loop provides high-concurrency request handling with minimal latency. Express offers a clean, unbloated framework for RESTful routing.

Vanilla JavaScript (ES6+): Native JavaScript with modern Fetch API eliminates heavy framework dependencies (like React or Angular), ensuring sub-second initial page loads and clean maintainability.

Chapter 3: Database Design & Architecture

3.1 Three-Tier Architecture Model

The system strictly decouples the user interface, business rules, and data storage:

┌─────────────────────────────────────────────────────────────┐
│ PRESENTATION TIER (Client Browser) │
│ HTML5 Semantics | Responsive CSS Variables | Vanilla JS │
└──────────────────────────────┬──────────────────────────────┘
│ HTTP / HTTPS (JSON via Fetch)
▼
┌─────────────────────────────────────────────────────────────┐
│ APPLICATION TIER (Node.js + Express) │
│ REST API Router | Business Validation | Pool Orchestration │
└──────────────────────────────┬──────────────────────────────┘
│ TCP Port 5432 (pg Parameterized)
▼
┌─────────────────────────────────────────────────────────────┐
│ DATA TIER (PostgreSQL Relational DB) │
│ Table: books | Sequence: books_id_seq | ACID Constraints │
└─────────────────────────────────────────────────────────────┘

3.2 Data Flow Diagram (DFD)

At Level 0, the Librarian submits catalog and circulation requests and receives real-time book tables, fine reports, and CSV streams. At Level 1, requests are partitioned into: (1) Connection Manager, (2) Catalog Search & Filter Engine, (3) Circulation Controller, (4) Fine Calculation Module, and (5) CSV Export Serializer.

3.3 Entity-Relationship (ER) Design

The central entity is BOOK, characterized by attributes: id, title, author, isbn, category, status, borrower, borrower_id, issue_date, due_date, and created_at.

3.4 Relational Schema & Integrity Constraints

  • Primary Key (PK): id ensures unique row identification.
  • Unique Constraint (UK): isbn prevents duplicate registrations.
  • Domain Constraint: status IN ('Available', 'Issued') restricts circulation states.
  • Entity Integrity: Essential columns (title, author, isbn, category) are marked NOT NULL.

3.5 Complete Data Dictionary

Column Name Data Type Constraints Description
id SERIAL PRIMARY KEY Auto-incrementing unique internal identifier
title VARCHAR(255) NOT NULL Full publication title of the book
author VARCHAR(255) NOT NULL Author(s) or editor(s) of the book
isbn VARCHAR(20) NOT NULL, UNIQUE International Standard Book Number (ISBN-10/13)
category VARCHAR(100) NOT NULL Academic faculty or literary genre
status VARCHAR(10) CHECK IN ('Available', 'Issued') Current circulation state (defaults to 'Available')
borrower VARCHAR(255) NULL Full name of student/borrower holding the item
borrower_id VARCHAR(50) NULL Official student/enrollment identification code
issue_date DATE NULL Calendar date on which book was checked out
due_date DATE NULL Scheduled return deadline for the book
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP Audit timestamp marking when record was entered
DBMS Technical Note on SERIAL Behavior:
In PostgreSQL, SERIAL creates an underlying sequence object (books_id_seq). When records are deleted, deleted sequence numbers are intentionally not recycled. This preserves referential integrity and audit trails. To prevent visual display confusion, the frontend displays an independent, unbroken sequential index (#1, #2, #3...) while preserving the true immutable database ID behind the scenes.

4.1 PostgreSQL Connection Pooling & DDL Schema

The backend initializes a resilient connection pool in backend/db.js supporting local and cloud SSL configurations: 

const { Pool } = require('pg');
const path = require('path');
require('dotenv').config({ path: path.join(__dirname, '.env') });

const config = process.env.DATABASE_URL
    ? {
        connectionString: process.env.DATABASE_URL,
        ssl: { rejectUnauthorized: false }
    }
    : {
        user: process.env.DB_USER,
        host: process.env.DB_HOST,
        database: process.env.DB_NAME,
        password: process.env.DB_PASSWORD,
        port: process.env.DB_PORT
    };

const pool = new Pool(config);
module.exports = pool;

4.3 Frontend Interface & Dynamic DOM Manipulation

The frontend application is constructed as a reactive single-page architecture using native DOM APIs:

  • Dual View Switcher: Librarians can seamlessly toggle between a high-density Table View and a visual Card Grid View.
  • Sequential Continuous Numbering: Display rows are numbered consecutively (#1, #2, #3, ...) regardless of sequence gaps created by row deletions.
  • Theme Persistence: High-contrast Light and Dark themes stored in browser localStorage.
  • Non-blocking Debounced Search: 250ms debouncing eliminates excessive database queries during user typing.

4.4 Key Business Logic Modules

Dynamic Overdue Calculation & Penalty Logic

Overdue status is calculated directly within the SQL query engine during record retrieval: 

SELECT 
    id, title, author, isbn, category, status, borrower, borrower_id, 
    issue_date, due_date,
    CASE 
        WHEN status = 'Issued' AND due_date < CURRENT_DATE THEN (CURRENT_DATE - due_date)
        ELSE 0 
    END AS overdue_days,
    CASE 
        WHEN status = 'Issued' AND due_date < CURRENT_DATE THEN (CURRENT_DATE - due_date) * 1
        ELSE 0 
    END AS fine_amount
FROM books;

One-Click Loan Renewal Module

When a student requests an extension, clicking +7d Renew directly increments the existing due date by 7 calendar days via SQL UPDATE without requiring check-in and re-issuance.

CSV Export Serializer

The export engine iterates over the full catalog, sanitizes strings against delimiter collisions, and streams an RFC 4180-compliant CSV download attachment.

5.3 SSL/TLS Encryption & Channel Binding

External database connections to cloud providers require SSL transport encryption. In desktop pgAdmin 4, Render's external proxy operates on TLS termination. The connection was configured with:

  • SSL Mode: Require to enforce cryptographic transport over port 5432.
  • Channel Binding: Set to disable within pgAdmin connection parameters to bypass SCRAM proxy mismatch.
