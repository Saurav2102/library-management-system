Abstract

Traditional academic and institutional libraries frequently encounter operational friction when relying on legacy manual register systems or spreadsheet-based tracking. These outdated mechanisms suffer from data redundancy, lack of transaction audit trails, delayed fine enforcement, and vulnerability to human error during circulation workflows.

This project presents Library Management System, an enterprise-ready, responsive, full-stack database application developed to streamline modern academic cataloging and circulation tracking. The system adheres to a decoupled Three-Tier Architecture:

  • Presentation Tier: Built with high-performance Vanilla JavaScript, HTML5, and responsive CSS3, featuring dynamic DOM updates, real-time debounced filtering, sequential catalog numbering, dark/light theme persistence, dual visual view toggles (Table vs. Grid), and one-click CSV export.
  • Application Tier: Powered by a lightweight Node.js runtime executing an Express.js RESTful API, enforcing robust input validation, parameter binding against SQL injection, and modular route dispatching.
  • Data Tier: Driven by an ACID-compliant PostgreSQL relational database with high-concurrency connection pooling (pg.Pool), domain check constraints, sequence generators, and auto-seeding routines.

The production system was seeded with an authentic dataset of 221 published academic textbooks and literary classics spanning 8 distinct faculties. It has been deployed to a live cloud infrastructure hosted on Render with TLS/SSL encryption and continuous delivery pipelines integrated via GitHub. Empirical evaluation proves instant sub-100ms response times for catalog lookups, automatic overdue penalty calculations, and zero-loss transaction guarantees.

Chapter 1: Introduction

1.1 Project Overview

An academic library serves as the intellectual nerve center of any higher educational institution. At institutions like K.R. Mangalam University, maintaining an orderly repository of thousands of technical books, reference manuals, journals, and literary works is critical for supporting teaching and student research.

The Library Management System engineered in this project is a modern web application designed to digitize the complete lifecycle of library inventory: acquisition, categorization, availability status, student checkout, loan renewals, overdue penalty auditing, and data export. It bridges the gap between complex enterprise relational databases and an intuitive, zero-friction user interface accessible across desktops, tablets, and smartphones.

1.2 Problem Statement

Historically, libraries used physical ledger cards or un-normalized desktop spreadsheets (such as MS Excel) to track borrowed books. These manual paradigms exhibit severe structural vulnerabilities:

  • Lack of Real-Time Concurrency: Multiple librarians attempting to update records simultaneously cause file-lock conflicts and lost data.
  • Data Integrity Degradation: Lack of relational integrity constraints allows duplicate ISBNs, misspelled categories, and invalid borrower associations.
  • Inaccurate Penalty Tracking: Calculating overdue fines manually requires labor-intensive date arithmetic, often resulting in uncollected institutional revenue.
  • Security and Audit Gaps: Excel files can be accidentally deleted or tampered with without audit logs or access control checks.

1.3 Purpose and Objectives

The primary objectives achieved in this project include:

  1. Automated CRUD Operations: Complete Create, Read, Update, and Delete capabilities through real SQL queries executed on PostgreSQL.
  2. Instant Circulation Workflow: Single-click book checkout and return with student ID recording and customizable loan durations.
  3. Dynamic Overdue & Fine Auditing: Automatic calculation of past-due days and fine penalties ($1.00 per day) updated in real time upon page retrieval.
  4. Data Portability: Native export of catalog records to RFC 4180-compliant CSV files for external administrative audits.
  5. Production Cloud Accessibility: Publicly reachable cloud deployment backed by encrypted database storage.

1.4 Scope and Limitations

The scope of this minor project covers full catalog browsing, searching, real-time filtering by status and department, single-click loan renewal, record editing, and analytics dashboards. While the current version accommodates administrative management, future phases will introduce multi-user role authentication and barcode scanner hardware integration.

2.3 Technology Stack Justification

PostgreSQL: Chosen over NoSQL or basic MySQL due to its strict ACID compliance, sophisticated sequence generators (SERIAL), support for declarative CHECK domain constraints, and rock-solid reliability in institutional transactional environments.

Node.js & Express.js: Node's non-blocking, asynchronous event loop allows the backend to handle high-concurrency client requests with negligible CPU overhead. Express provides a streamlined routing framework for clean RESTful JSON endpoints.

Vanilla JavaScript (ES6+): Instead of relying on heavy frontend frameworks (such as React or Angular) that introduce massive node_modules bundles and compilation overhead, standard native JavaScript with modern Fetch API was chosen for lightning-fast page loads and crystal-clear maintainability.

Chapter 3: System Design & Architecture

3.1 Three-Tier Architecture Model

The application enforces strict separation of concerns through an enterprise three-tier pattern:

┌─────────────────────────────────────────────────────────────┐
│ PRESENTATION TIER (Client Browser) │
│ HTML5 Semantics | CSS3 Variable Theming | Vanilla JS │
└──────────────────────────────┬──────────────────────────────┘
│ HTTP / HTTPS (JSON via Fetch)
▼
┌─────────────────────────────────────────────────────────────┐
│ APPLICATION TIER (Node.js + Express) │
│ REST API Router | Business Validation | Pool Orchestration │
└──────────────────────────────┬──────────────────────────────┘
│ TCP Port 5432 (pg Parameterized)
▼
┌─────────────────────────────────────────────────────────────┐
│ DATA TIER (PostgreSQL Relational DB) │
│ Table: books | Sequence: books_id_seq | ACID Constraints │
└─────────────────────────────────────────────────────────────┘

3.2 Data Flow Diagram (DFD Level 0 & Level 1)

At Level 0, the Librarian acts as the primary external entity submitting catalog inputs (book details, borrowing requests) and receiving processed query views (inventory status, fine warnings, and CSV exports).

At Level 1, requests are partitioned into five functional subsystems: (1) Authentication & Connection Manager, (2) Catalog Search & Filter Engine, (3) Circulation & Loan Controller, (4) Fine Calculation Module, and (5) CSV Serialization Processor.

3.3 Entity-Relationship (ER) Design

The primary entity is BOOK, defined by the attributes: id, title, author, isbn, category, status, borrower, borrower_id, issue_date, due_date, and created_at.

3.4 Relational Schema & Integrity Constraints

Relational integrity is maintained at the database engine level:

  • Primary Key (PK): id uniquely identifies every book record.
  • Unique Constraint (UK): isbn prevents duplicate registrations of the same publication.
  • Domain Check Constraint: status IN ('Available', 'Issued') enforces valid circulation states.
  • Entity Integrity: Mandatory columns (title, author, isbn, category) are marked NOT NULL.

3.5 Data Dictionary

The physical schema structure for the core books entity is detailed below:

Column Name Data Type Constraints Description
id SERIAL PRIMARY KEY Auto-incrementing unique internal identifier
title VARCHAR(255) NOT NULL Full publication title of the book
author VARCHAR(255) NOT NULL Author(s) or editor(s) of the book
isbn VARCHAR(20) NOT NULL, UNIQUE International Standard Book Number (ISBN-10/13)
category VARCHAR(100) NOT NULL Academic faculty or literary genre
status VARCHAR(10) CHECK IN ('Available', 'Issued') Current circulation state (defaults to 'Available')
borrower VARCHAR(255) NULL Full name of student/borrower holding the item
borrower_id VARCHAR(50) NULL Official student/enrollment identification code
issue_date DATE NULL Calendar date on which book was checked out
due_date DATE NULL Scheduled return deadline for the book
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP Audit timestamp marking when record was entered
DBMS Technical Note on SERIAL Behavior:
In PostgreSQL, SERIAL creates an underlying sequence object (books_id_seq). When records are deleted, deleted sequence numbers are intentionally not recycled. This preserves referential integrity and audit trails. To prevent visual display confusion, the frontend displays an independent, unbroken sequential index (#1, #2, #3...) while preserving the true immutable database ID behind the scenes.

4.1 Database Layer (PostgreSQL)

The database was instantiated using native SQL DDL statements. The connection pool is initialized in backend/db.js with support for both local development and cloud SSL connection strings:

const path = require('path');
require('dotenv').config({ path: path.join(__dirname, '.env') });

const config = process.env.DATABASE_URL

    : {

const pool = new Pool(config);

The backend exposes eight cleanly decoupled RESTful endpoints communicating via JSON:

4.3 Frontend Interface & Dynamic DOM Manipulation

The frontend application is constructed as a reactive single-page architecture using native DOM APIs. Key user-facing components include:

  • Dual View Switcher: Librarians can seamlessly toggle between a high-density Table View (for quick batch scanning) and a visual Card Grid View (displaying category tags and quick action buttons).
  • Sequential Continuous Numbering: Regardless of database sequence gaps, row items are labeled consecutively (#1, #2, #3, ...) via index + 1 mapping.
  • Theme Persistence: Supports high-contrast Light and Dark themes stored in the browser's localStorage, dynamically altering CSS custom properties.
  • Non-blocking Debounced Search: Input listeners on the search bar trigger search requests after a 250ms quiet period, eliminating redundant server calls on rapid typing.

4.4 Key Business Logic Modules

Dynamic Overdue Calculation & Penalty Logic

Overdue status is calculated directly within the SQL query engine during record retrieval, ensuring exact consistency across clients: 

SELECT 
    id, title, author, isbn, category, status, borrower, borrower_id, 
    issue_date, due_date,
    CASE 
        WHEN status = 'Issued' AND due_date < CURRENT_DATE THEN (CURRENT_DATE - due_date)
        ELSE 0 
    END AS overdue_days,
    CASE 
        WHEN status = 'Issued' AND due_date < CURRENT_DATE THEN (CURRENT_DATE - due_date) * 1
        ELSE 0 
    END AS fine_amount
FROM books;

One-Click Loan Renewal Module

When a student requests an extension, the librarian clicks the +7d Renew button. The backend parses the current due date, increments the calendar by 7 days, and writes the new due date without requiring the book to be checked in and re-entered.

CSV Export Serializer

The export engine iterates over the full catalog, sanitizes strings against CSV delimiter collisions (escaping double quotes per RFC 4180 standards), and emits the appropriate HTTP response headers (Content-Type: text/csv and Content-Disposition: attachment; filename="library_books_export.csv").

5.3 SSL/TLS Encryption & Channel Binding

External database connections to cloud providers require SSL transport encryption. During pgAdmin 4 desktop integration, Render's external proxy operates on TLS termination. The connection was configured with:

  • SSL Mode: Require to enforce cryptographic encryption over TCP port 5432.
  • Channel Binding: Set to disable within pgAdmin parameters to prevent SCRAM authentication mismatch across cloud reverse proxies.

This dual setup allows the local pgAdmin administrative GUI on the librarian's desktop to inspect and modify the exact same tables that the public web application serves.
